The problem

Every strategy, risk report and execution algorithm sits on top of a market-data pipeline, and most production bugs in quant research are data bugs: a duplicated bar, a silent gap, a return computed across a weekend, a VWAP over the wrong window. This project is a small but honest version of that layer. It ingests from free APIs, stores data in SQL with constraints, keeps ingestion idempotent and incremental, reports data quality, and computes the standard rolling statistics in the database.

Architecture

  1. Sources. Coinbase Exchange candles (300 per request, paged; minutes with no trades are simply absent) and Kraken OHLC (latest 720 minutes). Requests retry with exponential backoff on HTTP 429 and 5xx.
  2. Validation. Each bar must be minute-aligned, have positive prices, have a high and low that bracket the open and close, and have non-negative volume. Rejects are counted and reported, never silently dropped. The same rules exist again as CHECK constraints in the schema.
  3. Storage. SQLite table bars with primary key (symbol, ts). Writes are an upsert (INSERT … ON CONFLICT DO UPDATE), so re-running is idempotent and the still-forming latest minute is corrected on the next run. Each run writes an audit row to ingest_runs. Ingestion is incremental: it starts from the last stored minute.
  4. Analytics in SQL. Window functions compute every statistic inside the database. The query files in sql/ are executed unchanged by Python's sqlite3 and by sql.js in this page. The correlation query pivots both symbols onto one row per minute instead of joining two return series. The first version's join ran as a nested loop, and the rewrite made it about 10× faster.
  5. Quality report. Coverage, missing minutes, number and length of gaps, OHLC violations and zero-volume bars, per symbol.

Statistics

Windows are defined in time, not rows: RANGE BETWEEN (w−1)·60 PRECEDING AND CURRENT ROW on the timestamp. A missing minute then shrinks the sample instead of silently stretching the window back in time. Values stay empty until at least 80% of the window is present.

VWAP uses the typical price \( \tilde p_i = (H_i + L_i + C_i)/3 \) as a proxy, since one-minute bars do not show where inside the minute each trade happened. The session version anchors at 00:00 UTC.

\[ \text{VWAP}_t = \frac{\sum_{i \in W_t} \tilde p_i\, v_i}{\sum_{i \in W_t} v_i}. \]

Realised volatility. Log returns \( r_i = \ln(C_i / C_{i-1}) \) are taken between consecutive bars. A return spanning more than five minutes is discarded rather than stitched across an outage. Variance is additive in time, so dividing by the minutes actually covered keeps the estimate unbiased when minutes are missing. Crypto trades around the clock, so annualise by \( 525{,}600 \) minutes:

\[ \hat\sigma_{\text{ann}} = \sqrt{\frac{\sum_{i \in W_t} r_i^2}{\sum_{i \in W_t} \Delta t_i / 60}\times 525{,}600}, \qquad \hat\sigma^{\text{Park}}_{\text{ann}} = \sqrt{\frac{1}{4\ln 2}\,\overline{\big(\ln H_i/L_i\big)^2}\times 525{,}600}. \]

The Parkinson estimator uses each bar's high-low range, which carries more information per bar than the close alone. Comparing the two is itself a diagnostic: close-to-close estimates at one-minute sampling are inflated by bid-ask bounce (microstructure noise), while range estimates are biased low by discrete trading.

Correlation uses only synchronous one-minute returns, minutes where both symbols traded in that minute and the one before. It is computed in one pass from running sums:

\[ \hat\rho_t = \frac{n S_{xy} - S_x S_y}{\sqrt{(n S_{xx} - S_x^2)(n S_{yy} - S_y^2)}}. \]

Results

On the recorded 24-hour sample (Coinbase, 1,440 bars per symbol, no gaps, no rejects), 60-minute realised volatility had a median of 34% annualised for BTC-USD and 51% for ETH-USD. The BTC–ETH 60-minute correlation had a median of 0.88, ranging from 0.71 to 0.97. Parkinson volatility ran about 10% below close-to-close volatility for both. That is consistent with microstructure noise inflating one-minute close-to-close returns. A second ingest immediately afterwards fetched zero new rows, which shows that ingestion is incremental.

Testing

  • SQL against Python references. On synthetic bars with 3- and 8-minute holes, rolling VWAP, realised volatility and rolling correlation from SQL match deliberately naive Python loops to nine decimal places, including window membership and the sample count \( n \).
  • Statistical sanity. Realised volatility recovers the true volatility of a 20,000-minute simulated series within 2%. Correlation of two series with a known common factor recovers the true 0.49. A series correlated with itself gives exactly 1, and a flat price gives zero volatility.
  • Storage. Upserts are idempotent; a newer version of a bar replaces the old one; invalid bars are rejected with reasons; CHECK constraints reject a bad row even if validation is bypassed; session VWAP resets at midnight UTC; the quality report counts gaps exactly.
  • Sources. Coinbase paging (three requests for 700 minutes), column reordering and error payloads; Kraken parsing and errors; HTTP retry with exponential backoff on 429, using a fake transport so tests never touch the network.

Limitations

  • One-minute bars, not ticks. VWAP uses the typical price as a proxy for the true trade-weighted price, and the rolling statistics cannot see inside a minute.
  • A single venue per run. Consolidating venues would need symbol mapping, clock alignment and handling for venue-specific outages.
  • SQLite is the right tool at this scale, millions of rows on a laptop. Tick data for many symbols belongs in a columnar store (DuckDB, ClickHouse, kdb+, Parquet) partitioned by date and symbol.
  • There is no scheduler in the repository. Run the CLI from cron or a workflow; the ingest is incremental and safe to repeat.
