The problem

An exchange receives a stream of instructions: buy 150 at 100.02 or better, sell 40 at whatever the market will pay, cancel order 4,812. The matching engine has to decide, deterministically and quickly, who trades with whom and at what price. Nearly every venue uses price-time priority. The best price trades first. Among orders at the same price, the one that arrived first trades first.

That rule turns the design into a data-structure problem. The engine needs the best price on each side instantly, the oldest order at that price instantly, and it must be able to pull any order out of the middle of a queue when it is cancelled.

Data structures

Each side of the book is three structures working together.

  • A sorted array of active prices, ordered from worst to best so the best price is the last element. Reading the touch is O(1), and removing an exhausted best level is a pop(). A new level is found by binary search. Most new levels appear at or near the touch, so the splice usually moves only a few elements.
  • A hash map from price to level, so adding to an existing level skips the search entirely.
  • A FIFO queue per level, built as an intrusive doubly linked list. Each order carries its own prev/next pointers, so appending, taking the head, and unlinking from the middle are all O(1). The level keeps a running total quantity and order count for the depth view.

A global map from order id to order object lets a cancel jump straight to the order and unlink it.

OperationCostWhy
Best bid / best askO(1)last element of the price array

Depth snapshot, n levelsO(n)walk back from the end of the array

I chose the sorted array over a balanced tree on purpose. With L in the hundreds, a contiguous array of integers beats a pointer-chasing tree on cache behaviour, and activity concentrates near the touch, where insertion is cheapest. A tree would win if orders arrived uniformly across thousands of distant levels. Production engines with a bounded price band often go further and use a flat array indexed by tick offset from a reference price, which makes every level lookup O(1).

Matching rules

  • Prices are integer ticks. 100.03 is stored as 10003 with a 0.01 tick, so equality and ordering are exact and no floating-point error can split a level.
  • A buy matches while \( p_{\text{best ask}} \le p_{\text{limit}} \) (a sell while \( p_{\text{best bid}} \ge p_{\text{limit}} \)). Market orders have no limit and walk the book until filled or the book is empty.
  • The trade price is the resting order's price. The passive (maker) side set the price; an aggressive limit through the touch gets price improvement.
  • Partial fills. Each fill trades \( q = \min(q_{\text{incoming}}, q_{\text{resting}}) \). A partially filled resting order keeps its place at the head of its queue. A partially filled incoming limit order rests its remainder at its limit price.
  • Market orders are immediate-or-cancel. Any unfilled remainder is cancelled and never rests.
  • Invariant: after every event the book is uncrossed, \( p_{\text{best bid}} < p_{\text{best ask}} \).

Simulated order flow

The live market and the benchmark share one flow model, loosely after Cont, Stoikov and Talreja (2010). A latent fair value \( F \) follows a random walk in ticks. Limit orders arrive at rate \( \lambda_L \) and market orders at rate \( \lambda_M \). Each resting order is cancelled independently at rate \( \theta \), so with \( N \) orders resting the next event is a cancel with probability

\[ P(\text{cancel}) = \frac{\theta N}{\lambda_L + \lambda_M + \theta N}. \]

Cancellation that grows with the size of the book gives it a stable equilibrium depth: with the defaults, about 3,000 resting orders spread over 60 to 100 price levels per side. A limit buy is priced at \( \operatorname{round}(F) - \delta \) and a sell at \( \operatorname{round}(F) + \delta \), where \( \delta = \lfloor X \rfloor - 1 \) and \( X \sim \mathrm{Exp}(\text{mean } 10) \) ticks. Since \( P(\delta = -1) = 1 - e^{-0.1} \approx 9.5\% \), about one limit order in ten is priced through fair value and is likely to trade on arrival. Sizes are lognormal with mean 20.

Benchmark

The benchmark draws every random number for the whole stream before the clock starts, then times only the replay. Inside the timed loop the harness does two things besides calling the engine: it picks the event type from a pre-drawn uniform, and it maintains the list of resting ids that cancels target. A warm-up pass on a different stream runs first so the JIT has compiled the hot paths.

On Node 22 (one core of a shared cloud VM) the median of five runs over 1,000,000 events is 3.3 to 4.0 million operations per second across repeated sessions, roughly 250 to 300 ns per operation. The stream is 65% limit orders, 4% market orders and 32% cancels, and produces about 356,000 trades. Timing each call separately gives a median of about 170 ns and a 99th percentile under 1 µs. The 99.9th percentile is a few microseconds, which is garbage collection and timer noise rather than the algorithm.

These are single-threaded, in-process numbers with no network, persistence or risk checks. Production engines quote similar or better figures in C++ or Rust with pre-allocated memory; the point here is that the data structures, not the language, set the shape of the cost.

Testing

  • Rule tests for FIFO at one price, price priority across levels, maker-price execution, partial fills on both sides, queue position after a partial fill, market-order sweep and IOC residual, cancels from the middle of a queue, and rejection of invalid input.
  • Differential test against a deliberately naive reference matcher that re-sorts the whole book on every order. Over 15,000 random events across five seeds, the engine's trades (price, quantity, maker id, taker id) and final depth match exactly.
  • Invariant checks during a 20,000-event simulation: prices sorted, level totals equal the sum of their queues, FIFO sequence increasing, the id index in sync, no empty levels, book uncrossed, and traded volume conserved.

Run them with npm test, and the benchmark with npm run bench.

Limitations

  • Single instrument, single thread, in memory. There is no journal or replay log, so a crash loses the book.
  • No self-trade prevention, no order amend (cancel and resubmit loses queue priority, which matches most venues), and no IOC/FOK or post-only flags on limit orders.
  • No opening or closing auction, and no tick-size or price-band validation beyond positive integer ticks.
  • JavaScript garbage collection adds tail latency. A production engine would pre-allocate orders in a pool and avoid allocating trade objects on the hot path.
  • The splice into the price array is O(L) in the worst case, for a new level far from the touch on a very deep book.
